# killall-agents

Agent catalog and project setup for Claude Code, Codex, and Cursor (beta). Ordinary workflow skills live in [killall-skills](https://github.com/killallgit/killall-skills).

## Install

Claude Code:

```text
/plugin marketplace add killallgit/killall-agents
/plugin install killall-agents@killall-agents
```

Codex:

```sh
codex plugin marketplace add killallgit/killall-agents
codex plugin add killall-agents@killall-agents
```

Cursor: install from `https://github.com/killallgit/killall-agents` in **Customize**.

Skills CLI (setup and rules only):

```sh
npx skills add killallgit/killall-agents
```

Includes `agent-setup` and `follow-the-rules`.

## Agent catalog

| Agent | Purpose |
| --- | --- |
| `git-janitor` | Runs the separately installed `killall-skills:git-janitor` skill in its own context |
| `git-janitor-investigator` | Collects read-only branch/worktree evidence for the janitor |
| `comment-janitor` | Reviews changed comments for useful intent |
| `hall-monitor` | Checks a diff against programming rules |

Claude Code loads these from the plugin. Mention `@agent-killall-agents:git-janitor` in a conversation to invoke the janitor directly. Keep `killall-skills` installed to use that agent's cleanup skill. The agent definitions use Claude frontmatter; Codex and Cursor use the project roles generated by setup instead of receiving these as native plugin agents.

## Project setup

Run `/killall-agents:agent-setup` in Claude Code, or `$agent-setup` in Codex. Setup discovers the project's checks and worktree conventions and writes an orchestrator plus planner, grunt, builder, reviewer and lane hall-monitor definitions. The catalog hall-monitor and lane hall-monitor are separate agents.

| Role | Claude model / effort | Codex model / effort |
| --- | --- | --- |
| Orchestrator (project manager) | Sonnet / medium | `gpt-6.1-sol` / medium |
| Planner | Opus / high | `gpt-6-astra` / high |
| Grunt (relays to Pi) | Haiku / low | `gpt-6-luna` / low |
| Builder | Sonnet / medium | `gpt-6.1-sol` / medium |
| Reviewer | Sonnet / high | `gpt-6.1-sol` / high |
| Lane hall-monitor | Haiku / medium | `gpt-6-luna` / medium |

One [template per role](skills/agent-setup/templates/) holds host settings; the [renderer](skills/agent-setup/scripts/render_agents.py) writes Claude Markdown, Codex TOML and Cursor Markdown/rules. Claude starts via the `agent` setting in `.claude/settings.json`, Codex via the managed block in `.codex/config.toml` for a trusted project, and Cursor via an always-applied rule. Cursor inherits its session model.

The orchestrator is the project manager: it asks the read-only planner for a lane plan and re-plans through it, then runs and tracks the lanes. It sends tasks that fit a 64K-token context to grunt, a thin wrapper that runs the local [Pi](https://github.com/earendil-works/pi) agent with Pi's default provider and model, and larger implementation to builders. Grunt needs `pi` on `PATH` with a ready provider. Claude's tool allowlist permits reading, searching and delegation; Codex and Cursor enforce delegation by instruction. Codex subagents inherit the session's permissions. Builders create worktrees; reviewers independently run checks and report evidence. Builders and hall-monitors require the included `follow-the-rules` skill to resolve on the host.

Rerun setup after updating the installed plugin to refresh owned definitions. Local edits to generated files are replaced; unrelated settings remain intact. Foreign settings require explicit approval before `--force`. Generated paths are locally excluded through `.git/info/exclude`; already-tracked files stay tracked.

Lane records remain at `~/.config/killall-skills/agents/state/<encoded-main-checkout>/`, honoring valid `XDG_CONFIG_HOME`. All hosts and linked worktrees of a checkout use that folder; different machines do not automatically share it. The [state guide](skills/agent-setup/templates/state.md) defines the small JSON protocol. Setup refreshes the guide but preserves lane JSON. Removal clears owned definitions and exclusions while preserving state. Codex needs write access to its worktrees and state folder, for example `codex --add-dir <state-folder>`.
